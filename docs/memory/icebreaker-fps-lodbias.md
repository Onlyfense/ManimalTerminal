Icebreaker dense-view fps hunt (2026-08-08), concluded. The ~30-45 fps views toward ship center with GPU ~40% / CPU ~35% (nothing saturated) were MAIN-THREAD DRAW SUBMISSION bound, and the root cause was **EFT's Object LOD quality slider bottoming out at lodBias 2.0** on scenes shipping 40k+ working LODGroups. Clamping bias to ~1.0 took a ~22ms dense-view frame to ~12ms (camMain 10-11.5ms → 3-5ms). `LodBiasClamp` config now defaults 1.0 on the map (live-apply, -1 = hands off). MaxLodClamp=1 sledgehammer added only a little more — LODs themselves work fine in the rip.

The 1:1 mapping is VERIFIED in the decompile: slider stores "Settings/Graphics/ObjectLodQuality" (float, default 2), validator `Mathf.Clamp(value, 2f, 4f)` in GraphicsSettingsClass hard-enforces the [2,4] floor, GameGraphicsClass.smethod_9 assigns it to QualitySettings.lodBias verbatim. EFT's CameraLodBiasController (scope FOV compensation) brackets its own mul/restore inside OnPreCull/OnPostRender — composes cleanly with our Update-phase clamp.

**Sub-2 bias artifact + fix**: bsg authored LODGroup CULL thresholds (the last LOD height, below which the object stops rendering, crossfaded) assuming bias >= 2 — at bias 1, aggressive cullers (furniture) fade out in plain sight. `LodCullFloor` config (default 0.005) walks all map LODGroups at raid load (sliced) and caps the last threshold so props only vanish when tiny on screen. The cull floor is REQUIRED company for a sub-2 default bias.

**THE REAL MECHANISM (user called it)**: the in-raid histogram showed **79,833 of 81,862 LODGroups are single-LOD** — no lower meshes exist for 97.5% of the map. LODGroups here are BSG's DISTANCE-CULLING system, not a detail system; "lod bias" scales how far props cull, and the fps win = culling props earlier than retail. The whole thing is one dial: effective cull distance ~ bias/threshold. Floor 0.005 alone (bias 1) = props live LONGER than retail = fps regressed. **SHIPPING DEFAULTS (user-tuned live, 08-08): bias 0.7 + floor 0.01.** Floor semantics: HIGHER = earlier culls = more fps + more pop; lower = solid further out. Both knobs live-apply mid-raid (LodCullFloor caches authored heights per raid and re-applies in ~0.5s). Only ~1.5k groups have real mesh ladders — swap savings are a rounding error next to cull savings.

Exonerated along the way (do not re-litigate):
- **Shadows**: user's shadowDist was already 40, cascades 2. Note QualitySettings.shadowCascades silently clamps to min 1 — "cascades 0" is NOT a shadows-off test; shadowDistance 0 is.
- **Occlusion culling**: retail 84k-cell native bake restored via RUNTIME GRAFT (no bundle rebuild: the grid component serializes only _gridData=null + _gridHash "065281ec5449481391979c8269072a13"; Patch_GraftNativeGrid prefixes PerfectCullingCrossSceneSampler.InitializeAutoCulling, AddComponents onto the bare Adaptive_grid GO, game does full init itself; needs the 231MB packed file in StreamingAssets/Culling_Data — File.Exists-gated, NOT in the mod zip, recopyable from the live 1.0 install). Worked first try, made no fps difference in the views that hurt — the map is not occlusion-bound. NativeCulling config default false stays.
- **Static batching**: the bundle pre-batches ~91% at build time; runtime StaticBatch only catches ~2.2k leftovers. The "doorway" name-exclusion scare was a nothing — doorway subtrees were already batch-flagged.
- **Upscaling**: user already runs DLSS quality; presentTail ~3-5ms — GPU was never the wall.

The tools (all in RenderEnvProbe, RaidFixPatches.cs):
- **[FrameSplit]** 10s line: frame = scripts + camMain + presentTail (+ fixedUpd/f, alive=bots). Hand-rolled via Camera.onPreCull..onPostRender bracket + WaitForEndOfFrame marker — **FrameTimingManager returns NOTHING in bsg's build** (no frame-timing-stats flag), don't reach for it again. camMain = view culling + draw submission = the batching/culling/LOD bucket; scripts = AI/animation/physics/mod Updates (~5-12ms, scales with bots); presentTail = render-thread/GPU wait.
- **[QualityCensus]** one-shot at raid start: shadows/lodBias/maxLOD/pixelLights/vsync/targetFps — log it BEFORE A/Bing values the game may already have (shadow clamps were a wasted round because the game was already at 40/2).
- Live QualitySettings clamps (ShadowDistanceClamp, ShadowCascadesClamp, LodBiasClamp, MaxLodClamp): re-asserted per frame, originals captured on first touch, restored on -1 and in OnDestroy.

**Retail-parity gap (08-08, user's live-1.1 raid: 129fps, 80-90 floor, GPU 77% actually fed)**: retail runs 2-3x our dense-view frame rate. Root candidate found in the decompile: BSG's **cell-based LODGroup autocull** — GClass1237 + AutocullLODGroupCell (per-cell `lodgroup.enabled` toggles, 150 cells/frame, driven by the packed bake via GClass1238.Query + CullingGridPreProcess._visibilityCells 15m cells). **In SPT 4.0's assembly (0.16-BETA era, NOT 1.0 — user correction 08-08) the system is DORMANT**: GClass1237.method_5 (cell builder from CullingGridContent) and method_1 (queue-fill scheduler) have NO callers, method_4 initializes List_0 empty; the retail 1.0 LEVEL data ships the cell grid (_visibilityCells restored into our bundle on the CullingGrid node) but EMPTY cell content tables. BSG completed/activated the system somewhere between 0.16 and the live client. We cannot use retail code — but the plan below never needed it: the dormant classes verifiably exist in SPT's own assembly, we supply only the missing callers + data. Resurrection plan (all pieces public): with NativeCulling ON (needs the 231MB packed file), after sampler creates gclass1237_0 — build AutocullLODGroupCell[] ourselves by bucketing map LODGroups into PreProc.VisibilityCells by bounds, assign GClass1237.List_0 AND BitArray_0 (sized!), then call gclass1237_0.method_1() on cell change (track PerfectCullingCrossSceneSampler.Int32_0); their Update/LateUpdate already run and drain queues. **GATE QUESTION ANSWERED (08-08, Insert probe): dead end.** Toggling 56k LODGroups within 40m changed NOTHING — no visual change, no felt fps change. In this 0.16-era engine, LODGroup.enabled is inert for both hiding and main-thread savings; live 1.1's version of this system works via engine changes we cannot data-patch. Renderer-level plan B (IcebreakerCellCull.cs, config `CellCull`): built 08-08 — retail's 84k-cell visibility via GClass1238.Query + our renderer.enabled toggles, runtime bounds bucketing, only-re-enable-what-we-disabled ownership, fail-open. **NEVER ENGAGED: GClass1238 is never constructed because CullingGridPreProcess is missing from the shipped bundle** (the Author 15 restore evidently didn't land it / its GuidComponent) — `[CellCull] no visibility-cell machinery after 60s`. Parked; wiring it needs a CullingGridPreProcess restore. Do NOT conclude "renderer disabling doesn't help" from CellCull raids — it never ran.

**FINAL SHIPPED DEFAULTS (user-tuned, 08-09 final): bias 0.7, far floor 0.1, near floor 0.006, outdoor radius 27.1m, indoor radius 19.49m, LampIntensity 2.0 (was 3.0), LightCullDistance 25m.** Config cleanup same day: `SsrQuality` RETIRED (clamp hardcoded to full-size in ApplySsrClamp — the fix is not optional), `StaticBatch` RETIRED (bundle ships 91% pre-batched; runtime pass caught ~2.2k leftovers, never measured a win — class deleted). Cell-tiered (15m cells, renderer-bounds bucketing — pivots cluster and collapsed to 79 cells on the first try), true-meters radius to cell bounds (whole-cell chebyshev steps made the sliders feel dead), indoor/outdoor radius split driven by EnvironmentManager.Instance.Environment (the restored 51-trigger retail system — the Indoor_*-scene volume fallback misses the ENGINE ROOM whose geometry lives in Design scenes), drain is MEMBER-granular (budgeting only between cells hitched triple-digit ms on dense-cell boundary crossings). [LodCullFloor] INDOOR/OUTDOOR log line announces which radius is live.

**THE ORIGINAL DESIGN (user's, 08-08): distance-TIERED cull floors** — IcebreakerLodCullFloor rebuilt as parallel-array cache (group/pos/orig/applied) + per-frame rolling sweep (20k checks or 1ms budget, full pass every ~4 frames): groups within `LodCullNearRadius` (default 30m) get `LodCullNearFloor` (0.002 — nothing dithers in your face), beyond it `LodCullFloor` (0.01 — the fps lever, now free to be aggressive). All three live; no watcher, no visibility bake, no 231MB file — works for every player. The old ApplyFloor/AppliedFloor/Rebuilding watcher machinery is GONE. With near protection, LodBiasClamp can go below 0.7 for more fps.

**VANILLA COMPARISON MEASURED (08-09, [PerfCensus] on a live Customs raid)**: `grid=True packed=True sampler1238=False autocullCells=-1 crossVolumes=0 gridContentComps=0 lodGroups=67669 oneLod=50226`. The cell autocull is dormant ENGINE-WIDE — vanilla maps run without it (no sampler, no tables, no cells). Vanilla's edge = factory-correct packed bake data (never ripped) + lighter authoring (67k groups, 26% with real LOD ladders vs our 81k at 2%). No missing engine system exists to steal; the LOD tier system is the correct and sufficient compensation. The [PerfCensus] one-shot (RenderEnvProbe, fires ~60s into any NON-icebreaker raid) stays in the build for future comparisons.

**GPU-BOUND PLAYERS ARE A DIFFERENT PROFILE (08-09 field report, yamaica)**: LampIntensity 3→0 "considerably" improved center-ship fps and the map is NOT dark at 0 (emissives + flares + ambient carry the look). The dev box never sees this (GPU ~50% idle). Mechanism (decompiled): all 1581 lamps are healed CullingLightObjects under the native CullingManager, which **FADES intensity across an authored 50→80m window and NEVER disables a light** — so lamp GPU cost persists inside the window. Our own distance light-culler STANDS DOWN when healed CLOs exist (BuildLightCuller) — the first `LightCullDistance` knob was therefore INERT on this map (governed an empty list; a "no effect" test on it was measuring nothing). **Real version (08-09 late): ApplyLamps clamps each CLO's _fadeStartDistance/_fadeEndDistance (+ method_3 recompute) so bsg's own machinery zeroes lamps at the configured distance. Default 25m (user call, matches their played config), range 20-80, live for lowering only (shrink is one-way per raid). F8's [LightCensus] line verifies the fade actually zeroes lamps beyond the window (litBeyond count). LampIntensity 0 also hard-disables the plain-lamp Light components now.** Lesson ×2: dev-box verdicts only bind CPU-side levers, and a knob must be verified to ENGAGE before its A/B means anything.

**Every lever now tested (08-09, final sweep): shadows dead** (map barely has any — rip lost baked lighting, lamps near-zero), **pixel lights dead** (clamped 5→1, zero change — map renders deferred; knob added and removed same day), **far plane moot** (nothing but ocean/ice past 450m; game slider floors at 1000 anyway, validator at 400).
