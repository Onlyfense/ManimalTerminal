Audited Fika-Plugin source (github.com/project-fika/Fika-Plugin, cloned 2026-07-28) against Icebreaker's patches. Verified facts:

- `FikaBackendUtils.IsServer` exists (Fika.Core.Main.Utils) — FikaBridge resolves it by simple type name (namespace has drifted between versions).
- `CoopGame : BaseLocalGame<EftGamePlayerOwner>` (Fika.Core.Main.GameMode) — NOT LocalGame, so any `LocalGame.*` attribute patch is silently inert in coop. Re-anchor onto `CoopGame.Create(... Profile profile, LocationSettingsClass.Location location, ... LocalRaidSettings localRaidSettings ...)` (internal static). Every peer creates its own CoopGame with its own profile → per-player local charges are the natural semantics.
- `FikaHostTransitController : LocalGameTransitControllerClass` overrides `InteractWithTransit` + `Transit` → patches on the LocalGame-class overrides never fire on a fika host. Clients run `ClientTransitController : GClass1906` (sibling branch).
- Patches on `TransitInteractionControllerAbstractClass` (method_14 entry gate, method_15 prompt gate) DO fire on every peer — it's the shared base of both fika controllers.
- The transit CONFIRM moment on every peer is `FikaPlayer.vmethod_3(TransitControllerAbstractClass, int transitPointId, string keyId, EDateTime)` (Fika.Core.Main.Players; host branch calls controller directly, client branch sends TransitInteractPacket). `ObservedPlayer` overrides it to do nothing → a prefix here charges exactly the traveler, locally, never remotely — avoids the inventory-desync trap from the fika wiki.
- Fika's own patches use `MainMenuControllerClass.method_53/55` → the vanilla menu flow (incl. our method_54 ready gate) runs for the HOST; joining clients use fika's lobby UI and may bypass it → the map-fare consume must be all-or-nothing (never partial-drain).
- Bots exist only on the host (clients get ObservedPlayer replicas; `BotOwner.Create` doesn't run client-side) → gate spawn systems on `FikaBridge.BotsAuthority`.
- **Fika INSTALLED ≠ fika IN USE** (08-05 field report): players carry Fika.Core as a
  dependency of other mods and raid solo — the raid runs plain LocalGame,
  `FikaBackendUtils.IsServer` stays false, and a pure-IsServer authority gate turns
  ALL crew/BD/knight spawning off with no host to pick it up (native BossLocationSpawn
  still trickles a few rogues, which disguises it as "barely any bots"). Fix in
  BotsAuthority: if `Singleton<AbstractGame>.Instance` is non-null and its type name
  doesn't contain "Coop", it's solo semantics → full authority; only a real CoopGame
  consults IsServer.

Implementation lives in icebreaker-client: FikaBridge.cs (reflection detection), IcebreakerFikaCompat.cs (runtime re-anchors, soft `BepInDependency("com.fika.core")` for load order), host gate in IcebreakerCrew.Run.

Any-player triggers implemented (phase 3): `FikaBridge.CollectHumans/AnyHumanIn/NearestHumanSqr/IsHumanPlayer` wrap `CoopHandler.TryGetCoopHandler` + `HumanPlayers` (List<FikaPlayer>, includes remote humans' ObservedPlayers whose Position is synced; handler is a MonoBehaviour — re-resolve when destroyed, mind Unity's overloaded null). Trigger layers (TierEventLogic/GroupSizeEventLogic), engine release box, cutscene box (video per-player, story beat any-player + host-authoritative), legacy watchers, and PickPoints player-exclusion all roster-aware. `GroupSize()` needed no change — GameWorld.RegisteredPlayers non-AI count already covers coop, so retail party-size brackets scale the BD response.

**The sanctioned inventory-op pattern** (verified in assembly + fika source, 07-28): create the op with **simulate:TRUE** (validates + builds the changeset, applies nothing), then dispatch via `controller.TryRunNetworkTransaction(gstruct, callback)` — it executes ONCE through `vmethod_1`, which fika overrides to replicate. BSG's BotDeadBodyWork (Move) and fika's ClientSharedQuestController (Remove) both do exactly this. simulate:false applies inline and is invisible to fika peers; simulate:false COMBINED with the transaction double-executes (`ExecuteInternal(Callback)` → `ExecuteInternal()` → `changeset.Execute()`) — that was the chain-door flashing-item bug. Exception: pre-raid profile mutations (map fare at game Create) have no live controller — bare grid removal there mirrors BSG's own labs-keycard flow. Transit fare + chain-door charge now use the sanctioned pattern; `BotsAuthority` fails CLOSED when fika is present but unresolved.

**Fika sync addon** (icebreaker-fika project, 07-28, modeled on bmpq/spt-ladders' ladders.fika): separate plugin `ManimalIcebreakerFika.dll`, GUID `com.manimal.icebreaker.fika`. THE FIKA DEP MUST STAY HARD (settled 08-03 after breaking it): a soft-dep self-gating build hard-hung the game PRE-MENU on solo installs — EFT's `GlobalEventHandlerClass.Initialize` sweeps every LOADED assembly with `Assembly.GetTypes()`, which throws ReflectionTypeLoadException on any assembly referencing the absent Fika.Core; no addon code needs to run to break, so NoInlining guards are useless. Only a bepinex load-SKIP (hard dep) keeps the assembly out of the appdomain. Shipping model per the 07-30 user call: the addon is its OWN zip for fika users — solo installs never have the dll (the red '1 PLUGIN FAILED TO LOAD' banner only appears if someone installs the addon without fika, which is correct feedback). If one-zip shipping is ever wanted, the pattern is a fika-free loader plugin + a NON-plugin sync assembly loaded manually behind the chainloader check. Also: this GetTypes-sweep failure is a likely cause of player 'infinite load before main menu' reports involving other mods. No reflection needed in the addon (compile-time ref to the real `Fika.Core.dll` at `$(FikaPath)\BepInEx\plugins\Fika\`, `FikaPath=D:\SPTDevFika` in Directory.Build.props, Private=false). Pattern: base mod raises C# events on LOCAL commits (suppressed during remote apply to prevent echo), addon subscribes → `SendData(ref packet, ReliableOrdered, broadcast:true)` (server auto-relays client sends) → receive handler calls the base mod's `ApplyRemote`. Packets: `struct : INetSerializable` registered via `FikaNetworkManagerCreatedEvent` → `manager.RegisterPacket<T>`; unregister via reflection on `_packetProcessor`. Base mod grants `[InternalsVisibleTo("ManimalIcebreakerFika")]`. Synced: chain-door plant/open (fuse+explosion deterministic, runs locally per peer), sealed-door seal/unseal by door.Id. D:\SPTDevFika is the fully-provisioned coop test install (full mod payload mirrored 07-28).

**Invisible-bots root cause (07-29, user's memory cracked it):** `ObservedCullingManager` is a retail scene singleton driving observed-BODY visibility — bots solo, remote players + bots on fika clients (same observed-body path). Missing on the backport; without it every observed body's visibility "Auto" resolves invisible → `forceRenderingOff=true` on the base body skins (head/shirt/pants) while gear renderers stay clean = floating-gear ghosts; damage/death un-hides via body-part refresh. The original fix created it in a `BotsController.Init` prefix — host-only hook, so fika clients regressed. Moved into `EnsureEnvAndWeather` (the universal `Player.Init` prefix), which is now the home for ALL "retail scene singletons our rip lacks, needed before player/body init": weather stack, EnvironmentManager, ObservedCullingManager. The addon F7 body probe (renderer dump w/ forceRenderingOff/layer/shader) found the flag; chainloader-time `AddComponent` MonoBehaviours never tick — create diag components at raid time.

**Coop field findings (07-28 two-player tests):** fika door sync (player+bot+keycard interactions) resolves via `World.FindDoor`'s id dictionary — on the backported map that registry misses the doors entirely (ripped scenes never do the LocationScene registration the world build reads), packets arrive `component exists, id unresolvable` on every peer; fixed by `RaidFixPatches.HealDoorRegistry` (register missing interactables via public `GameWorld.World_0.RegisterWorldInteractionObject`, deterministic sort). The acoustics door-id "stamping" never renames anything (authored ids == retail ids). Direct DoorState writes still need addon packets (progress door = kind 4). `Camera.main` is NULL in EFT — use `CameraClass.Instance.Camera`. Invisible-observed-rogues bug NOT explained by the shadow-proxy sweep (player-exclusion fix didn't cure it) — body probe (addon F7 + 20s sampler) is the open investigation. Headless clients: fika marks them by nickname prefix `headless_` (peers can check `Profile.Nickname.StartsWith("headless_")`); FikaBridge filters headless bodies out of the human roster (GroupSize/triggers). A headless host is the ideal solo repro rig for client-side bugs — it hosts, you join as a client.

**Keypad/passcode sync (2026-08-03, player-reported: host notes 005/487 vs client 342/239 on the same spots):** two-layer fix. (1) `FikaBridge.SharedRaidRng(salt)` — deterministic per-raid Random seeded by FNV-1a over `FikaBackendUtils.RaidCode + ServerGuid` (host generates at match create, clients receive via join result/FikaPingingClient BEFORE raid start — verified in Fika source; resolved by property reflection alongside IsServer). IcebreakerPasscodes draws codes, note-spot shuffle, and note variant from it → every peer independently computes identical codes+notes, zero packets, headless-safe. Determinism contract: same sidecar json + same rng draw ORDER — dont reorder draws in BuildAsync. Null when solo (local random) or when reflection drifts (logged). Reusable for any other per-raid RNG that must agree across peers. (2) the unlock itself is a direct `DoorState` write (Locked->Shut) fika never replicates — `Keypad.CommitUnlock` is now the single commit path (local + remote), `UnlockCommitted` event -> addon kind 13 packet -> `ApplyRemoteUnlock(doorId)`. Door-less terminals cant sync (no id, cosmetic only).

Still untested in a real coop session: door-state replication of our host-side unlock, heli exfil pay prompt under fika (EftGamePlayerOwner is shared by both game classes so it should fire, unverified), whether client-side local inventory ops (transit fare fake-stash move) survive fika's raid-end profile sync.

**Custom transit on fika (08-05, CORRECTED by live trace — version drift warning: repo HEAD differs from the running 2.3.9):** in 2.3.9 the CLIENT builds its own prompt from its enter chain (live trace: client `drove OnPlayerEnter` -> `method_14` PROMPT OFFERED with no host packet involved); repo HEAD moved prompts to host-sent TransitInteractionEvent.Show. THE once-per-raid prompt bug: 2.3.9's client exit chain does NOT clear `AvailableInteractionState`, and its enter chain refuses to re-offer while it's stale — fix: TransitZoneExitWatch force-calls `method_18(player)` (the idempotent clear) for the local player on every exit. Full working stack for the runtime hovercraft point: per-peer arming (method_8+method_2) + multi-human watch (per-ProfileId visits, drives OnPlayerEnter/Exit; AvailableInteractionState no-double gate LOCAL player only) + exit-clear + `method_14` PROMPT-OFFERED tap and Info drive logs for tracing. CoopGameCreatePrefix also captures IceGate.PendingLocationId (LocalGame.smethod_6 inert in coop). LESSON: when the cloned mod source is newer than the installed version, live-trace instrumentation beats source reading — the Show-packet model cost two wrong fixes.

**THE transit-prompt root cause (08-05, trace-solved after 5 wrong theories):** a HEADLESS host runs `FikaHeadlessTransitController` from the SEPARATE Fika-Headless repo (github.com/project-fika/Fika-Headless) — it derives from the BASE `TransitController`, NOT `TransitInteractionControllerAbstractClass`, and our drive's hard interaction-cast gate silently ate every enter-drive on the headless. Its `OnPlayerEnter` delegate does everything (own method_11 reimpl + Show packet), so the DELEGATE is the drive requirement; the interaction cast is only for the method_14 fallback + local prompt-state gate. The intermittent prompts users saw were Unity's native OnTriggerEnter firing flakily on the runtime box (trace: 14s late once, instant once, usually never). THREE fika transit controllers exist: FikaHostTransitController (LocalGame family, normal host), ClientTransitController (GClass1906 family), FikaHeadlessTransitController (base family, headless) — any transit code must handle all three. The restart-proof `icebreaker_transit_trace.log` (next to the plugin dll, ENTER/DRIVE/EXIT/PROMPT_OFFERED/GATE-BLOCKED/REBIND lines) is what cracked it — headless BepInEx logs get wiped by auto-restart.
